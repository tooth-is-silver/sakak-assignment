# 개미수열 알고리즘

이전 항의 연속된 같은 숫자를 개수와 숫자 순서로 읽어 다음 항을 만들고, n번째 항의 가운데 두 자리를 반환합니다.

## 실행 방법

저장소 루트에서 의존성을 설치한 뒤 `n`을 전달해 결과를 확인할 수 있습니다.

> [!WARNING]
> `n=99`는 유효한 입력이지만 `L99` 전체 문자열을 생성하려면 약 3,921억 자리를 메모리에 올려야 합니다. 직접 실행하면 테스트가 실패하거나 터미널이 응답하지 않을 수 있으므로 테스트와 벤치마크는 `n=30`까지만 수행합니다. `n=100` 이상은 실행 전에 입력 오류로 처리합니다.

```bash
npm install
npm run algorithm -- 5
```

```text
12
```

테스트와 벤치마크는 다음 명령으로 실행합니다.

```bash
npm run test:algorithm
```

위 명령은 결과·예외 처리 회귀 테스트와 `n=30` 재귀 풀이 벤치마크를 함께 실행합니다.

타입과 코드 규칙은 다음 명령으로 확인할 수 있습니다.

```bash
npm run typecheck --workspace algorithm
npm run lint --workspace algorithm
```

## 풀이 과정

수열의 정의를 그대로 코드로 옮기기 위해 재귀와 두 위치 인덱스를 사용했습니다.

1. 첫 번째 항이면 문자열 `1`을 반환합니다.
2. `n - 1`번째 항을 재귀 호출로 구합니다.
3. 이전 항을 왼쪽부터 한 번 순회합니다.
4. 같은 숫자 묶음의 시작 위치와 현재 위치의 차이로 개수를 계산합니다.
5. 개수와 숫자를 다음 항에 추가합니다.
6. n번째 항이 완성되면 가운데 두 자리를 반환합니다.

예를 들어 `111221`은 다음과 같이 변환합니다.

```text
111 → 31
22  → 22
1   → 11

312211
```

중첩 반복문 없이 현재 위치를 문자열 끝까지 한 번 이동합니다. 문자가 달라지거나 문자열 끝에 도달하면 하나의 숫자 묶음이 끝난 것으로 판단합니다.

### 검토한 다른 방법

정규식으로 연속된 같은 숫자를 묶는 방법도 검토했습니다. 예를 들어 `(\d)\1*` 패턴으로 같은 숫자가 이어지는 구간을 찾고, 일치한 문자열의 길이와 첫 번째 숫자를 조합하면 다음 항을 만들 수 있습니다.

정규식은 코드를 짧게 만들 수 있지만 묶음을 찾고 개수를 계산하는 과정이 패턴 안에 감춰집니다. 이 문제에서는 왼쪽과 오른쪽 위치가 어떻게 이동하고 묶음의 길이를 어떻게 계산하는지 코드에서 바로 확인할 수 있는 투 포인터 방식을 선택했습니다. 이전 항을 한 번 순회한다는 시간 복잡도도 투 포인터 방식이 더 분명하게 드러납니다.

## 함수별 책임

- `createNextTerm`: 이전 항을 한 번 순회해 다음 항 생성
- `getMiddleTwoDigits`: 두 자리 이상의 짝수 길이 항에서 가운데 두 자리 반환
- `getLookAndSayMiddleDigits`: 입력값 검증, n번째 항 생성, 최종 결과 반환

## 입력값과 가운데 두 자리 정책

최종 입력 `n`은 과제 조건에 맞춰 4 이상 99 이하의 정수만 허용합니다. 문자열·소수·`NaN`·무한대와 범위를 벗어난 값은 오류로 처리합니다.

홀수 길이 문자열은 가운데를 기준으로 왼쪽 두 자리, 오른쪽 두 자리 또는 가운데 한 자리 중 무엇을 반환해야 하는지 요구사항에 정의되어 있지 않습니다. 임의로 결과를 결정하지 않고, 가운데 두 자리가 명확한 두 자리 이상의 짝수 길이 숫자 문자열만 처리합니다.

## 테스트

구현 전에 테스트를 먼저 작성하고 다음 경우를 확인했습니다.

- 공개 함수의 입력과 최종 출력
- 과제 예시 `n=5 → 12`, `n=8 → 21`
- `n=4~10`, `12`, `15`, `20`, `30`의 결과
- number가 아닌 입력의 `TypeError`와 오류 메시지
- 범위 밖 숫자와 무한대의 `RangeError`와 오류 메시지
- 소수와 `NaN`의 오류 및 오류 메시지

현재 구현을 대상으로 자체 커버리지를 확인했으며 구문, 분기, 함수, 줄 커버리지가 모두 100%입니다.

## 시간·공간 복잡도

이전 항의 길이를 `|L(n-1)|`이라고 할 때 `createNextTerm`은 문자열을 한 번 순회합니다.

- 한 단계 시간 복잡도: `O(|L(n-1)|)`
- n번째 항 생성 시간 복잡도: `O(|L1| + |L2| + ... + |Ln|)`
- 문자열 공간 복잡도: `O(|L(n-1)| + |Ln|)`
- 재귀 호출 공간 복잡도: `O(n)`

재귀 깊이보다 각 항의 문자열 길이가 빠르게 증가하는 것이 주요 비용입니다.

## 최대 입력의 한계

OEIS A005341에 따르면 `L99`의 길이는 `392,187,941,864`자리입니다. 전체 문자열을 Node.js 프로세스 메모리에 만드는 직접 생성 방식으로는 현실적으로 처리할 수 없습니다.

반복문이나 정규식으로 구현을 바꿔도 전체 문자열을 만드는 비용은 없어지지 않습니다. 전체 항을 만들지 않고 필요한 위치만 추적하려면 Conway의 92개 원소와 변환 규칙을 이용하는 별도 풀이가 필요합니다.

이번 구현에서는 재귀 풀이의 정확성과 비용을 확인하는 데 집중했습니다. 실제 수열 생성 테스트와 벤치마크는 `n=30`까지 수행합니다. 로컬에서 측정한 `n=30`의 평균 실행 시간은 약 0.37ms였으며, 벤치마크는 환경 차이를 고려해 평균 100ms 미만인지 검사합니다.

## 소감

수열 규칙만 보면 이전 항을 순서대로 읽는 문제라 재귀와 단일 순회로 간단하게 표현할 수 있었습니다. 그러나 최대 입력을 검토하면서 함수 호출 횟수보다 생성되는 문자열 크기가 실제 병목이라는 점을 확인했습니다. 입력 범위와 필요한 출력이 가운데 두 자리뿐이라는 조건을 함께 보면 전체 문자열을 생성하지 않는 다른 접근이 필요하지만, 그 방법은 기본적인 개미수열 구현과는 다른 수학적 구조를 요구합니다. 구현이 동작하는 것뿐 아니라 입력 범위에서 실제로 실행 가능한지도 함께 확인해야 한다는 점이 가장 중요한 부분이었습니다.
